Trellis is easiest to understand by following one request from the moment you type it. The system is not a single daemon or a hidden service. It is a set of markdown contracts, task files, JSONL context manifests, local scripts, skills, sub-agents, and platform adapters that all point the AI at the right next action.

## From one user request

A persisted Trellis request follows this chain:

```text
User prompt
  -> SessionStart project map
  -> UserPromptSubmit workflow-state breadcrumb
  -> task persistence under .trellis/tasks/
  -> JSONL context routing
  -> skills and sub-agents
  -> hooks, extensions, or pull-based platform equivalents
  -> finish-work and workspace journal
  -> next session starts with better memory
```

Purely conversational requests can stop before task persistence. This page explains the durable-work path because that is where the architecture matters. For exhaustive file lists, hook wiring, or JSONL field references, use the reference pages linked at the end instead of treating this page as the source of every path.

## Session start gives the AI the project map

Before the AI answers a prompt, Trellis tries to load the map of the project.

On hook-capable platforms, the `SessionStart` hook or extension reads the local Trellis state and injects it into the session. On prelude-based platforms, the same idea is delivered through the platform's startup file, such as `AGENTS.md` for Codex or steering / workflow files on other tools.

The startup context usually includes:

- Developer identity from `.trellis/.developer`.
- The workflow contract from `.trellis/workflow.md`.
- Current git branch, git status, and recent commits.
- Active tasks under `.trellis/tasks/`.
- The developer workspace index under `.trellis/workspace/<developer>/`.
- Available package and spec layers from `.trellis/spec/`.

The important part is not the transport. The important part is that each session starts with the same project map, so the AI can see current tasks, relevant specs, and recent work without relying on chat history.

`get_context.py` is the local API behind much of this reporting. It can emit the full session context, package/spec summaries, and phase-specific workflow detail. `init_developer.py` and `get_developer.py` keep the per-machine developer identity separate from committed project files.

## Each prompt receives workflow state

After startup, each user message gets a smaller, more targeted nudge: the current workflow state.

`workflow.md` defines the Plan / Execute / Finish phases, skill routing, and the `<workflow-state>` breadcrumb text. When a platform supports `UserPromptSubmit`, Trellis injects the breadcrumb on every prompt. The breadcrumb tells the AI whether there is no active task, a planning task, an in-progress task, or a completed task that needs wrap-up.

The active task is session-scoped. `task.py start` records the task for the current AI session under `.trellis/.runtime/sessions/`, and `task.py current --source` exposes where that active-task state came from. This is why two AI windows can work on different tasks without overwriting each other.

See [Customizing the Workflow](./custom-workflow) for how `workflow.md` controls phases and breadcrumbs, and [Custom Hooks](./custom-hooks) for the event-level hook behavior.

## Work becomes a task when it needs persistence

Small answers can stay in the chat. Work that needs planning, research, code changes, or later verification becomes a Trellis task under `.trellis/tasks/<date-slug>/`.

A task directory is the durable workspace for one piece of work:

- `task.json` stores task metadata and lifecycle state.
- `prd.md` stores the requirements the implementer must satisfy.
- `info.md`, when present, stores technical design notes.
- `research/` stores persisted findings from investigation.
- `implement.jsonl`, `check.jsonl`, and `research.jsonl` route context into execution roles.

`task.py` is the task lifecycle API. It creates tasks, starts the current session on a task, clears or archives tasks, lists tasks, validates JSONL, and appends context entries. The architecture point is simple: task state lives in files, and the scripts provide a stable way for commands, hooks, skills, and humans to update those files consistently.

For command details, use [Appendix B](./appendix-b). For key path references, use [Appendix A](./appendix-a).

## JSONL routes context instead of dumping the repository

Trellis does not ask every sub-agent to read the whole repository before acting. Each task has JSONL manifests that say which rules and background material should be injected up front.

The manifests are routing files:

- `implement.jsonl` tells `trellis-implement` which specs and research to read before writing.
- `check.jsonl` tells `trellis-check` which quality and verification guidance to apply.
- `research.jsonl` gives `trellis-research` background for an investigation when needed.

Use JSONL for material the agent must know before it starts:

```jsonl
{"file": ".trellis/spec/docs-site/docs/index.md", "reason": "Docs-site writing and MDX rules"}
{"file": ".trellis/tasks/04-29-api-choice/research/options.md", "reason": "Persisted API comparison"}
```

Do not use JSONL as a source-code dump. Raw source files and directories usually belong outside the manifest because sub-agents already have file search and read tools. They should inspect code on demand instead of carrying stale code snippets in every prompt.

For the full JSONL reference, see [Appendix D](./appendix-d).

## Skills and sub-agents execute each phase

The workflow names the role that should act at each point:

- `trellis-brainstorm` turns unclear intent into `prd.md`, asks focused questions, and configures task context.
- `trellis-research` investigates code, docs, or third-party behavior and writes findings into `research/`.
- `trellis-implement` performs the implementation against `prd.md`, `info.md`, specs, and research.
- `trellis-check` reviews the diff, runs verification, and fixes issues it finds.
- `trellis-update-spec` decides whether a new convention or lesson should be written back into `.trellis/spec/`.
- `trellis-break-loop` is used when repeated debugging shows that a root cause needs a deeper retrospective.

On platforms with sub-agent primitives, implement and check work is delegated to `trellis-*` sub-agents. On platforms without sub-agents, the same roles are performed inline through skills and workflow instructions. The role boundary stays the same even when the platform transport changes.

For custom agent behavior, see [Custom Agents](./custom-agents). For custom skills, see [Custom Skills](./custom-skills).

## Hooks and platform equivalents sit in the request chain

Hooks are not a separate architecture layer bolted onto Trellis. They are the places where the request chain gets the context it needs:

- `SessionStart` builds the project map before the first answer.
- `UserPromptSubmit` adds the workflow-state breadcrumb to each prompt.
- Where the platform exposes sub-agent injection, `PreToolUse` on `Task` injects JSONL context before a Trellis sub-agent starts.
- Extension-backed platforms, such as Pi Agent, implement equivalent behavior through an extension rather than Python hook scripts.
- Pull-based sub-agent platforms put the same context-loading instructions inside the sub-agent prelude. The sub-agent resolves the active task, reads `prd.md`, and loads the JSONL files itself.
- Agent-less platforms have no hook or sub-agent primitive, so the main session runs the start workflow and skills directly.

That gives Trellis three delivery modes with the same underlying architecture:

- Hook or extension push: context is injected before the AI or sub-agent acts.
- Pull-based prelude: the AI or sub-agent is instructed to read the same files at the start of its turn.
- Inline workflow: the main session reads the workflow and specs directly, then performs the role without delegation.

Use [Multi-Platform and Team Configuration](./multi-platform) for the current platform matrix and [Custom Hooks](./custom-hooks) for hook configuration details.

## Scripts are the local APIs behind the chain

The scripts under `.trellis/scripts/` are small local APIs used by commands, hooks, skills, and humans:

- `task.py`: task lifecycle API for create, start, current, finish, archive, list, context validation, and context entry updates.
- `get_context.py`: context/report API for session summaries, package/spec discovery, and workflow phase detail.
- `add_session.py`: workspace journal API that appends a session entry and updates the developer index.
- `init_developer.py` and `get_developer.py`: developer identity helpers for the local checkout.
- `hooks/linear_sync.py`: optional lifecycle integration for syncing task create, start, archive, and sync events with Linear.

The design goal is that platform-specific commands stay thin. They call these scripts instead of reimplementing task state, context discovery, or journal writing in every platform template.

## Finish-work writes memory for the next session

The request chain ends when work is verified and recorded.

`finish-work` coordinates the final steps:

1. Confirm the quality gate has passed, including relevant lint, type-check, tests, and spec compliance.
2. Remind the human to review and commit the work. Trellis does not commit the project diff before that review.
3. Archive completed tasks with `task.py archive`.
4. Record the session with `add_session.py`.

The journal entry lands in `.trellis/workspace/<developer>/journal-N.md`, and the workspace index is updated for future session startup. `add_session.py` writes Trellis workspace/task metadata and auto-commits those metadata changes by default unless you pass `--no-commit`; it is not the mechanism for committing implementation changes. On the next `SessionStart`, Trellis can surface that history as part of the project map.

This is why Trellis treats memory as a file-system concern. Chat context may disappear, but task files, research artifacts, specs, and journals remain available to every platform.

## Architecture recap

| Layer                  | Main files or entry points                                      | Architectural role                                      |
| ---------------------- | --------------------------------------------------------------- | ------------------------------------------------------- |
| Workflow control plane | `.trellis/workflow.md`                                          | Defines phases, routing, and per-prompt breadcrumbs     |
| Session context        | `SessionStart`, `get_context.py`, `.trellis/.developer`         | Gives the AI project identity, status, and map          |
| Prompt-time state      | `UserPromptSubmit`, `.trellis/.runtime/sessions/`               | Keeps each prompt aligned to the current task phase     |
| Task persistence       | `.trellis/tasks/<task>/`, `task.py`                             | Stores requirements, metadata, research, and context    |
| Context routing        | `implement.jsonl`, `check.jsonl`, `research.jsonl`              | Chooses specs and research without dumping source code  |
| Execution roles        | Trellis skills and `trellis-*` sub-agents                       | Separates planning, research, implementation, checking  |
| Platform adapters      | Hooks, extensions, preludes, workflow files                     | Delivers the same workflow across different AI tools    |
| Workspace memory       | `add_session.py`, `.trellis/workspace/<developer>/journal-N.md` | Carries finished-session knowledge into future sessions |
| Optional integrations  | `.trellis/scripts/hooks/linear_sync.py`                         | Connects task lifecycle events to external systems      |
