理解 Trellis 架构，最直接的方法不是先背组件表，而是跟着一条请求走完整链路。Trellis 不是一个隐藏 daemon，也不是某个平台专属的黑盒。它由 markdown 契约、任务文件、JSONL 上下文清单、本地脚本、skill、sub-agent 和平台适配层组成，让 AI 在每一步都能拿到正确的上下文和下一步动作。

## 从一条用户请求开始

需要持久化的 Trellis 请求会沿着这条链运行：

```text
用户提示词
  -> SessionStart 项目地图
  -> UserPromptSubmit workflow-state 面包屑
  -> .trellis/tasks/ 下的任务持久化
  -> JSONL 上下文路由
  -> skill 与 sub-agent 执行
  -> hook、extension 或 pull-based 平台等价机制
  -> finish-work 与 workspace journal
  -> 下一个 session 带着更好的记忆启动
```

纯对话型请求可以在任务持久化之前结束。下面按 durable work 的路径解释架构，因为那里才需要这些部件协作。完整文件路径、hook 配置和 JSONL 字段表放在文末引用页；架构页只说明这些部件为什么会在请求链上出现。

## SessionStart 给 AI 项目地图

AI 回答第一条提示词之前，Trellis 会尽量先加载项目地图。

在支持 hook 的平台上，`SessionStart` hook 或 extension 会读取本地 Trellis 状态并注入到会话里。在 prelude 型平台上，同一件事由平台启动文件承载，比如 Codex 的 `AGENTS.md`，或其他工具的 steering / workflow 文件。

启动上下文通常包括：

- `.trellis/.developer` 里的开发者身份。
- `.trellis/workflow.md` 里的工作流契约。
- 当前 git 分支、git 状态和最近提交。
- `.trellis/tasks/` 下的活跃任务。
- `.trellis/workspace/<developer>/` 下的开发者 workspace 索引。
- `.trellis/spec/` 里的 package 与 spec layer。

关键不在传输方式，而在所有 session 都以同一份项目地图开场。AI 不需要依赖聊天记忆，就能看到当前任务、相关规范和近期工作。

`get_context.py` 是这类报告背后的本地 API。它可以输出完整会话上下文、package/spec 摘要和某个 workflow phase 的详细说明。`init_developer.py` 和 `get_developer.py` 负责本机开发者身份，让个人身份和提交到仓库的项目文件分开。

## 每条提示词都收到 workflow state

启动之后，每条用户消息还会收到更短、更精确的提醒：当前 workflow state。

`workflow.md` 定义 Plan / Execute / Finish 阶段、skill 路由和 `<workflow-state>` 面包屑文本。平台支持 `UserPromptSubmit` 时，Trellis 会在每条提示词上注入这段面包屑。面包屑告诉 AI 当前是没有活跃任务、规划中、执行中，还是已完成但需要收尾。

活跃任务是 session-scoped 的。`task.py start` 会把当前 AI session 绑定到某个任务，并写入 `.trellis/.runtime/sessions/`；`task.py current --source` 可以显示这个 active-task 状态来自哪里。因此两个 AI 窗口可以同时做不同任务，不会互相覆盖。

想改 phase 和面包屑，看[定制 Workflow](./custom-workflow)。想看事件级 hook 行为，看[定制 Hook](./custom-hooks)。

## 需要持久化时，请求变成任务

很小的回答可以停留在聊天里。需要规划、调研、改代码或后续验证的工作，会变成 `.trellis/tasks/<date-slug>/` 下的 Trellis task。

一个 task 目录就是一项工作的持久 workspace：

- `task.json` 保存任务元数据和生命周期状态。
- `prd.md` 保存 implementer 必须满足的需求。
- `info.md` 如存在，保存技术设计说明。
- `research/` 保存调研产物。
- `implement.jsonl`、`check.jsonl`、`research.jsonl` 把上下文路由给不同执行角色。

`task.py` 是任务生命周期 API。它创建任务、把当前 session 切到某个任务、清理或归档任务、列出任务、校验 JSONL，并追加上下文条目。架构重点是：任务状态存在文件里，脚本给 command、hook、skill 和人提供一致的更新入口。

命令细节见[附录 B](./appendix-b)。关键路径见[附录 A](./appendix-a)。

## JSONL 负责路由上下文，而不是倾倒仓库

Trellis 不要求每个 sub-agent 动手前读完整仓库。每个任务用 JSONL manifest 声明哪些规则和背景资料需要提前注入。

这些 manifest 是路由文件：

- `implement.jsonl` 告诉 `trellis-implement` 写代码前要读哪些 spec 和 research。
- `check.jsonl` 告诉 `trellis-check` 要按哪些质量和验证规则检查。
- `research.jsonl` 在需要调研时给 `trellis-research` 背景材料。

JSONL 应该放 agent 动手前必须先知道的内容：

```jsonl
{"file": ".trellis/spec/docs-site/docs/index.md", "reason": "Docs-site writing and MDX rules"}
{"file": ".trellis/tasks/04-29-api-choice/research/options.md", "reason": "Persisted API comparison"}
```

不要把 JSONL 当源码 dump。原始源码文件和目录通常不该进 manifest，因为 sub-agent 自己有文件搜索和读取工具。需要看代码时，它应该按需搜索，而不是每次 prompt 都携带可能过期的代码片段。

完整 JSONL 参考见[附录 D](./appendix-d)。

## Skill 和 sub-agent 执行各阶段

workflow 会在每个阶段指定该由哪个角色行动：

- `trellis-brainstorm` 把模糊意图变成 `prd.md`，提出聚焦问题，并配置任务上下文。
- `trellis-research` 调研代码、文档或第三方行为，并把结果写入 `research/`。
- `trellis-implement` 根据 `prd.md`、`info.md`、spec 和 research 完成实现。
- `trellis-check` 审查 diff、运行验证，并修复发现的问题。
- `trellis-update-spec` 判断新的约定或经验是否需要写回 `.trellis/spec/`。
- `trellis-break-loop` 用于同一类 bug 反复出现时的根因复盘。

支持 sub-agent 原语的平台会把 implement 和 check 交给 `trellis-*` sub-agent。没有 sub-agent 的平台，则由主会话通过 skill 和 workflow 指令内联完成。同一个角色边界会保留，只是平台传输方式不同。

自定义 agent 见[定制 Agent](./custom-agents)。自定义 skill 见[定制 Skill](./custom-skills)。

## Hook 和平台等价机制就在请求链上

Hook 不是独立于 Trellis 的附加层。它们是请求链上注入上下文的位置：

- `SessionStart` 在第一次回答前构建项目地图。
- `UserPromptSubmit` 在每条提示词上追加 workflow-state 面包屑。
- 在平台提供 sub-agent 注入点时，`PreToolUse` 匹配 `Task` 并在 Trellis sub-agent 启动前注入 JSONL 上下文。
- Pi Agent 这类 extension-backed 平台用 extension 实现同等行为，而不是加载 Python hook 脚本。
- Pull-based sub-agent 平台把相同的上下文加载指令写进 sub-agent prelude。sub-agent 自己解析活跃任务、读取 `prd.md`，再加载 JSONL。
- Agent-less 平台没有 hook 和 sub-agent 原语，主会话直接运行 start workflow 与 skill。

因此 Trellis 有三种交付模式，但底层架构相同：

- Hook 或 extension push：AI 或 sub-agent 动作前，上下文已经被注入。
- Pull-based prelude：AI 或 sub-agent 在回合开始时按指令读取同一批文件。
- Inline workflow：主会话直接读取 workflow 和 spec，并在不委派的情况下完成对应角色。

当前平台能力矩阵见[多平台与团队配置](./multi-platform)。Hook 配置细节见[定制 Hook](./custom-hooks)。

## 脚本是请求链背后的本地 API

`.trellis/scripts/` 下的脚本是 command、hook、skill 和人共同调用的小型本地 API：

- `task.py`：任务生命周期 API，负责 create、start、current、finish、archive、list、context validation 和 context entry 更新。
- `get_context.py`：上下文与报告 API，负责 session 摘要、package/spec 发现和 workflow phase 详情。
- `add_session.py`：workspace journal API，追加 session 记录并更新开发者索引。
- `init_developer.py` 与 `get_developer.py`：当前 checkout 的开发者身份工具。
- `hooks/linear_sync.py`：可选生命周期集成，用于把 task create、start、archive、sync 事件同步到 Linear。

设计目标是让平台专属 command 保持很薄。它们调用这些脚本，而不是在每个平台模板里重新实现任务状态、上下文发现或 journal 写入。

## Finish-work 把记忆写给下一次 session

请求链的末尾，是验证和记录。

`finish-work` 负责串起最后几步：

1. 确认 quality gate 已通过，包括相关 lint、type-check、test 和 spec compliance。
2. 提醒人类 review 并提交本次 work。Trellis 不在 review 前替用户提交项目 diff。
3. 用 `task.py archive` 归档已完成任务。
4. 用 `add_session.py` 记录本次 session。

Journal entry 会写到 `.trellis/workspace/<developer>/journal-N.md`，workspace index 也会更新，供下次 SessionStart 读取。`add_session.py` 会写入 Trellis workspace/task 元数据，并且默认自动提交这些元数据变更；传 `--no-commit` 可以跳过。它不是提交实现改动的入口。这就是为什么 Trellis 把记忆设计成文件系统能力：聊天上下文会丢，任务文件、research、spec 和 journal 会留下来给所有平台继续使用。

## 架构回顾

| 层级              | 主要文件或入口                                                  | 架构职责                                |
| ----------------- | --------------------------------------------------------------- | --------------------------------------- |
| Workflow 控制平面 | `.trellis/workflow.md`                                          | 定义 phase、路由和每轮面包屑            |
| Session 上下文    | `SessionStart`、`get_context.py`、`.trellis/.developer`         | 给 AI 项目身份、状态和地图              |
| Prompt-time 状态  | `UserPromptSubmit`、`.trellis/.runtime/sessions/`               | 让每条提示词对齐当前任务阶段            |
| Task 持久化       | `.trellis/tasks/<task>/`、`task.py`                             | 保存需求、元数据、research 和 context   |
| Context 路由      | `implement.jsonl`、`check.jsonl`、`research.jsonl`              | 选择 spec 和 research，不倾倒源码       |
| 执行角色          | Trellis skill 与 `trellis-*` sub-agent                          | 分离规划、调研、实现和检查              |
| 平台适配层        | hook、extension、prelude、workflow file                         | 在不同 AI 工具中交付同一套 workflow     |
| Workspace 记忆    | `add_session.py`、`.trellis/workspace/<developer>/journal-N.md` | 把已完成 session 的知识带到未来 session |
| 可选集成          | `.trellis/scripts/hooks/linear_sync.py`                         | 把任务生命周期事件连接到外部系统        |
